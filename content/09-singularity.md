# 9. Singularity와 Apptainer의 이해

> **학습 방식:** 이론과 명령 읽기 · 40~50분
> **준비:** 2장의 이미지·컨테이너 개념 · 설치 불필요

**학습 목표:** Docker와 Apptainer의 공통점과 차이를 설명하고, 실행 사용자·파일 연결·접근 권한을 구분합니다. 연구 클러스터에서 Apptainer와 Slurm이 맡는 역할도 이해합니다. 이 장의 명령은 읽기용입니다. 지금 터미널에서 실행하지 않습니다.

## 1. Docker를 배웠는데 왜 다른 도구가 나오나요?
2장에서 종이를 자르는 일을 떠올렸습니다. 작업 설명서만 있어서는 부족하고, 가위와 자도 필요했습니다. 이미지는 이 도구와 실행 환경을 준비한 작업 세트였습니다.

**Docker도, Singularity도, Apptainer도 준비된 도구로 작업하도록 돕는 컨테이너 도구입니다.** 새로운 종류의 분석을 배우는 것이 아니라, 준비된 분석 환경을 사용하는 다른 방법을 알아보는 것입니다.

```text
하고 싶은 일: 준비된 분석 프로그램으로 내 데이터 처리하기
    ├─ 개인 PC에서는 Docker Desktop으로 연습
    └─ 연구 서버에서는 서버가 제공하는 Apptainer 등을 사용
```

Docker도 연구 서버에서 사용할 수 있습니다. 실제로 어떤 도구를 사용할지는 서버 관리자가 제공하는 환경과 사용 규칙에 따릅니다.

## 2. 공용 연구실에 도구 세트를 가져온다고 생각해 보세요
내 책상에서는 내가 원하는 도구를 설치하고 사용할 수 있습니다. 하지만 여러 사람이 함께 쓰는 연구실에서는 규칙이 있습니다.

- 다른 사람의 서랍을 열거나 파일을 바꾸면 안 됩니다.
- 작업 자리를 혼자 다 차지하면 안 됩니다.
- 관리자가 허용한 도구와 방법으로 작업해야 합니다.

Apptainer는 이런 **여러 사용자가 함께 쓰는 연구 서버와 대규모 계산 환경**에서 사용하기 좋게 만들어졌습니다. 일반적인 실행에서는 내 사용자 계정의 권한으로 작업합니다. 컨테이너를 실행했다고 서버 관리자 권한이 생기지는 않습니다.

> **“준비된 도구를 가져와서, 내 권한으로, 연구실 규칙에 맞게 작업한다.”**

Docker의 일반적인 구성에서는 Docker 엔진이 컨테이너를 만들고 실행합니다. Apptainer는 Docker 같은 상시 실행 엔진 없이 이미지 파일을 지정해 프로그램을 실행할 수 있습니다. Docker에도 일반 사용자 권한으로 동작하는 방식이 있으므로 “Docker는 무조건 관리자만 사용한다”라고 이해하지는 마세요.

## 3. Singularity와 Apptainer는 왜 이름이 두 개인가요?
처음에는 **Singularity**라는 이름의 프로젝트에서 출발했습니다. 이후 프로젝트가 나뉘어 현재는 **Apptainer**와 **SingularityCE**가 각각 개발되고 있습니다. 공통 역사를 가진 별도 프로젝트입니다.

연구실에서 “Singularity로 실행하세요”라고 말하면, 실제로 설치된 도구가 무엇인지 확인하면 됩니다. 안내문에 `singularity` 또는 `apptainer`라는 명령 이름이 나올 수 있습니다.

이 교재의 예시는 `apptainer`로 통일합니다. 두 도구를 모두 설치하거나 이름의 역사를 외울 필요는 없습니다. **서버에서 제공하는 도구와 버전을 확인하는 것**이 중요합니다.

## 4. .sif 파일은 준비된 작업 세트예요
Apptainer에서는 프로그램과 실행 환경을 **`.sif`라는 이미지 파일**에 담아 사용할 수 있습니다.

```text
analysis.sif = 분석 도구가 준비된 이미지 파일
samples.tsv  = 내가 분석할 입력 파일
result.txt   = 분석해서 만든 결과 파일
```

`.sif`는 사진 파일도, 분석 결과도 아닙니다. 앞에서 배운 **Docker 이미지처럼 준비된 도구와 실행 환경을 담은 것**입니다. 파일을 내려받거나 복사해 둔다고 분석이 자동으로 시작되지는 않습니다.

| 구분 | 쉽게 기억하기 |
|---|---|
| 이미지 파일 `.sif` | 준비된 작업 세트 |
| 컨테이너 실행 | 그 세트의 도구를 사용해 작업하기 |
| 입력 파일 | 자를 종이 |
| 결과 파일 | 잘라서 완성한 종이 |

기본 SIF 이미지는 읽기 전용으로 사용합니다. 결과를 이미지 안에 넣으려 하지 말고, 서버의 결과 폴더에 저장합니다.

### Docker에서 배운 것과 나란히 비교해 보세요
**SIF 파일은 Dockerfile이 아니라 Docker 이미지에 해당합니다.** Dockerfile은 준비 방법을 적은 설명서이고, SIF는 프로그램과 실행 환경을 이미 준비해 둔 작업 세트입니다.

| 하는 일 | Docker | Apptainer | 종이 자르기 비유 |
|---|---|---|---|
| 이미지를 만드는 방법 작성 | `Dockerfile` | 정의 파일 `.def` | 어떤 가위와 자를 준비할지 적은 설명서 |
| 프로그램과 실행 환경 준비 | Docker 이미지 | SIF 이미지 파일 `.sif` | 가위와 자를 준비한 작업 세트 |
| 이미지 내려받기 | `docker pull` | `apptainer pull` | 준비된 작업 세트를 가져오기 |
| 준비된 환경에서 명령 실행 | `docker run` | `apptainer exec` | 도구를 꺼내 실제 종이를 자르기 |
| 입력·출력 폴더 연결 | `--mount` | `--bind` | 종이와 완성품을 보관할 폴더 연결하기 |

```text
Dockerfile → 이미지 만들기 → Docker 이미지 → 컨테이너에서 작업 실행
.def 파일  → 이미지 만들기 → .sif 파일    → 컨테이너에서 작업 실행
```

두 설명서의 문법과 실행 옵션은 다릅니다. 위 표는 역할을 비교한 것이며, 명령을 그대로 바꿔 쓰면 된다는 뜻은 아닙니다. 이번에는 Dockerfile이나 `.def`를 직접 작성하지 않고, 이미 만들어진 이미지를 사용합니다.

Docker에서는 보통 **로컬 Docker 저장소에 있는 이미지 이름**을 지정합니다. 이 장의 Apptainer 예시에서는 **서버에 저장한 `.sif` 파일의 경로**를 지정합니다. 그래서 `alpine:3.21`과 `alpine.sif`는 같은 역할의 작업 세트를 가리키지만, 저장하고 부르는 방식이 다릅니다.

**Docker 이미지도 파일로 내보낼 수 있고, Apptainer도 이미지 저장소의 주소를 직접 사용할 수 있습니다.** 여기서는 처음 배우기 쉽게 가장 기본적인 사용 흐름을 비교합니다.

## 5. 명령 한 줄을 읽어 봅시다
**아래는 Apptainer가 설치된 Linux 환경에서 사용할 수 있는 예시입니다. 이번 수업에서는 실행하지 않고 뜻만 읽습니다.**

먼저 도구 세트를 준비하는 명령입니다.

```bash
apptainer pull alpine.sif docker://alpine:3.21
```

<details markdown="1"><summary>명령 한 줄씩 해석하기</summary>

| 명령 또는 부분 | 하는 일 |
|---|---|
| <code>apptainer pull alpine.sif docker://alpine:3.21</code> | Docker Hub의 이미지를 가져와 alpine.sif라는 로컬 이미지 파일로 준비합니다. 도구를 내려받는 단계이며 아직 분석을 실행하지 않습니다. |
| `alpine:3.21` | 기본 도구를 갖춘 작은 Alpine Linux 이미지입니다. 3.21은 이미지의 태그입니다. |

</details>


| 부분 | 뜻 |
|---|---|
| `apptainer pull` | 사용할 이미지를 내려받아 준비합니다. |
| `alpine.sif` | 만들어 둘 로컬 이미지 파일의 이름입니다. |
| `docker://alpine:3.21` | Docker Hub의 Alpine 이미지를 가져와 SIF 파일로 준비합니다. |

**Docker 이미지를 가져올 수 있지만, 이 명령을 실행하는 데 Docker Desktop이 필요한 것은 아닙니다.** Apptainer가 이미지 저장소에서 데이터를 가져옵니다. 모든 Docker 작업이 그대로 호환되는 것은 아닙니다.

이제 준비된 도구로 인사를 출력합니다.

```bash
apptainer exec alpine.sif echo hello
```

<details markdown="1"><summary>명령 한 줄씩 해석하기</summary>

| 명령 또는 부분 | 하는 일 |
|---|---|
| <code>apptainer exec alpine.sif echo hello</code> | 지정한 SIF 이미지 안의 echo로 hello를 출력합니다. 파일 연결이나 결과 파일 저장은 하지 않습니다. |
| `echo 글자` | 컨테이너 안에서 지정한 글자를 출력합니다. >가 있으면 그 출력을 파일에 저장합니다. |

</details>


왼쪽부터 **“Apptainer로 → 이 이미지의 환경에서 → echo hello를 실행한다”**라고 읽으세요.

| Docker에서 배운 명령 | Apptainer에서 읽어 볼 명령 |
|---|---|
| `docker run --rm alpine:3.21 echo hello` | `apptainer exec alpine.sif echo hello` |

둘 다 결과는 `hello`입니다. Docker는 이미지 이름을, 이 Apptainer 예시는 로컬 `.sif` 파일을 지정합니다. 실행 방식과 옵션이 모두 같다는 뜻은 아닙니다.

## 6. 내 파일과 결과 폴더는 어떻게 연결하나요?
7장에서 Docker의 `--mount`로 폴더를 연결했습니다. Apptainer에서도 폴더를 연결할 수 있습니다. 다음 예시는 입력 파일의 줄 수를 세고 서버의 출력 폴더에 저장합니다.

**읽기용 예시 · 서버에 input/output 폴더, 입력 파일과 alpine.sif가 준비되어 있다고 가정합니다.**

```bash
apptainer exec \
  --bind "$PWD/input:/input:ro" \
  --bind "$PWD/output:/output" \
  alpine.sif sh -c 'wc -l /input/samples.tsv > /output/line-count.txt'
```

<details markdown="1"><summary>명령 한 줄씩 해석하기</summary>

| 명령 또는 부분 | 하는 일 |
|---|---|
| <code>apptainer exec  --bind &quot;$PWD/input:/input:ro&quot;  --bind &quot;$PWD/output:/output&quot;  alpine.sif sh -c &#x27;wc -l /input/samples.tsv &gt; /output/line-count.txt&#x27;</code> | 지정한 SIF 이미지의 환경에서 뒤의 명령을 실행합니다. `--bind`는 서버 폴더:컨테이너 경로 순서이며 `:ro`는 읽기 전용입니다. 이 장에서는 실행하지 않고 읽습니다. |
| `sh -c / bash -c` | 해당 셸이 따옴표 안의 명령을 해석합니다. 컨테이너 명령 뒤의 >가 컨테이너 내부에서 처리되도록 할 수 있습니다. |
| `> 경로` | 표준 출력을 파일에 저장합니다. 파일을 만들거나 덮어쓰지만 상위 폴더까지 만들지는 않습니다. |
| `$PWD` | 현재 작업 폴더의 절대 경로입니다. |
| `wc -l` | 입력 파일이나 전달받은 입력의 줄 수를 셉니다. 예제는 헤더를 포함해 4줄입니다. |

</details>


| 부분 | 뜻 |
|---|---|
| `$PWD/input:/input:ro` | 서버의 현재 폴더 안 input을 컨테이너의 /input에 읽기 전용으로 연결합니다. |
| `$PWD/output:/output` | 서버의 output을 컨테이너의 /output에 연결합니다. |
| `alpine.sif` | 사용할 도구 세트입니다. |
| `sh -c '...'` | 이미지 안의 셸에서 따옴표 안 명령을 실행합니다. |
| `wc -l /input/samples.tsv` | 입력 파일의 줄 수를 셉니다. |
| `> /output/line-count.txt` | 화면에 나올 결과를 연결한 출력 폴더의 파일에 저장합니다. |

```text
서버의 input/samples.tsv    → 컨테이너의 /input/samples.tsv
서버의 output/line-count.txt ← 컨테이너의 /output/line-count.txt
```

**폴더 연결은 저장 경로를 이어 주고, 프로그램과 `>`가 실제 결과 파일을 만듭니다.** Docker 실습과 같은 생각입니다. Apptainer는 홈 폴더 등 일부 경로를 기본 연결하기도 하지만, 실제 연결 범위는 서버 설정에 따라 다릅니다. 여기서는 입력·출력 위치를 분명히 보려고 직접 지정했습니다.

## 7. 스크립트와 컨테이너는 역할이 달라요
Apptainer 명령은 일반 프로그램처럼 실행하므로 스크립트와 비슷하게 느껴집니다. 하지만 **Apptainer는 Docker와 같은 컨테이너 도구**입니다. 스크립트와 Docker 이미지의 중간 단계가 아닙니다.

| 구분 | 일반 스크립트 | Apptainer 컨테이너 | Docker 컨테이너 |
|---|---|---|---|
| 준비하는 것 | 실행할 명령과 코드 | 프로그램과 라이브러리를 포함한 환경 | 프로그램과 라이브러리를 포함한 환경 |
| Python 등은 어디서 가져오나요? | 호스트에 설치된 환경 | 이미지 내부 환경 | 이미지 내부 환경 |
| 패키지 버전 | 별도 환경 관리 필요 | 이미지에 포함해 관리 | 이미지에 포함해 관리 |
| 실행 관리 | 셸이나 인터프리터 | 사용자 명령으로 실행, 상시 데몬 불필요 | Docker 데몬이 관리 |
| 기본 실행 사용자 | 실행한 호스트 사용자 | 실행한 호스트 사용자 | 이미지의 USER 또는 실행 옵션 |
| 호스트 폴더 | 계정 권한 범위에서 접근 | 기본 연결 및 직접 지정한 폴더 | 직접 연결한 폴더 |

**스크립트는 “무슨 일을 할지”, 이미지는 “어떤 프로그램 환경에서 할지”를 정합니다.** 분석 스크립트를 Apptainer 또는 Docker 안에서 실행할 수 있습니다. 두 컨테이너 도구 모두 일반적인 Linux 실행에서는 호스트 커널을 공유하며, 별도의 Linux 커널을 부팅하는 가상 머신이 아닙니다.

## 8. 실행 사용자는 누가 정하나요?
이 절의 Docker 예시는 **Linux의 일반적인 root 권한 데몬 구성** 기준입니다. Docker Rootless, 사용자 네임스페이스, macOS·Windows의 Docker Desktop에서는 호스트와 UID가 대응하는 방식이 달라질 수 있습니다. Apptainer는 기본 실행 기준이며, 관리자 실행이나 fakeroot는 별도 동작입니다.

### 사용자 이름보다 UID·GID를 확인하세요
Linux는 파일 소유자와 권한을 판단할 때 숫자 ID를 사용합니다. UID는 사용자 ID, GID는 그룹 ID입니다. 이름이 같아도 UID가 다르면 같은 소유자로 취급되지 않습니다.

```text
서버 사용자 seon: UID 1000, GID 1000
이미지 사용자 app: UID 2000, GID 2000
```

Dockerfile에 `USER 2000:2000`이 있으면 Docker는 기본적으로 UID 2000으로 프로그램을 실행합니다. 호스트의 seon이 명령을 입력했다고 컨테이너 프로그램도 UID 1000으로 실행되는 것은 아닙니다. USER 설정이 없는 이미지는 일반적으로 컨테이너 내부 root로 실행됩니다.

**동일한 Docker 이미지를 Apptainer로 가져오면 기본 실행에서는 USER 설정을 무시하고, 실행한 호스트 사용자의 UID·GID로 프로그램을 실행합니다.** 같은 이미지를 여러 연구자가 사용해도 각자의 권한으로 작업합니다.

| 상황 | Docker | Apptainer 기본 실행 |
|---|---|---|
| 이미지에 USER 2000:2000 지정 | UID 2000, GID 2000 | 호스트 사용자의 UID·GID |
| 호스트 UID 1000이 실행 | 이미지 설정에 따라 다름 | UID 1000 |
| 결과를 연결된 호스트 폴더에 생성 | 실행 UID에 따라 소유자 결정 | 기본적으로 호스트 사용자 소유 |
| 다른 사람 파일 접근 | 실행 권한과 연결 상태 등에 따라 결정 | 기존 호스트 계정의 접근 권한 유지 |

Docker에서도 실행 사용자를 지정할 수 있습니다. 아래 명령은 읽기용입니다.

```bash
docker run --rm --user "$(id -u):$(id -g)" alpine:3.21 id
apptainer exec alpine.sif id
```

`id -u`는 내 UID, `id -g`는 기본 GID를 출력합니다. `$(...)`는 호스트 셸이 명령을 실행해 그 출력으로 바꿉니다. 마지막 `id`는 컨테이너 안에서 실행합니다. Docker의 `--user`는 이미지의 기본 사용자를 덮어씁니다.

> **주의:** Docker에서 숫자 UID·GID를 맞추어도 이미지 안에 해당 사용자 이름이나 홈 폴더가 생기는 것은 아닙니다. 호스트의 보조 그룹도 이 옵션만으로 모두 전달되지는 않습니다. 프로그램에 따라 추가 설정이 필요합니다.

컨테이너 내부 root와 호스트 전체 관리자 권한을 동일하게 생각하지 마세요. Docker는 기본적으로 권한을 제한하지만, 일반적인 root 데몬에 자유롭게 명령을 보낼 수 있는 권한은 호스트 root 수준의 제어를 허용할 수 있습니다. 이것이 공용 서버에서 Docker 사용 권한을 신중하게 제공하는 이유입니다. Docker에도 Rootless 방식이 있습니다.

## 9. 파일은 “보이는가”와 “권한이 있는가”를 따로 확인해요
폴더 연결은 파일을 보이게 하는 일이고, 권한은 그 파일을 사용할 수 있는지를 결정합니다. **연결했다고 읽기·쓰기 권한이 새로 생기는 것은 아닙니다.**

| 확인할 조건 | 의미 | 문제가 있을 때 |
|---|---|---|
| 호스트 폴더가 연결되었나요? | 원하는 호스트 파일이 컨테이너에 보이는가 | 파일 없음 또는 이미지 내부의 다른 폴더가 보임 |
| 실행 사용자에게 권한이 있나요? | UID·GID, 보조 그룹, ACL 등에서 접근을 허용하는가 | Permission denied |
| 읽기 전용 연결인가요? | 마운트 자체가 쓰기를 허용하는가 | 사용자에게 쓰기 권한이 있어도 쓰기 실패 |

### 자동으로 연결되는 폴더의 차이
Docker는 호스트의 홈과 현재 작업 폴더를 자동으로 연결하지 않습니다. Apptainer는 기본 설정에서 홈과 현재 작업 폴더 등을 연결합니다. 관리자 설정과 경로 조건에 따라 달라질 수 있으므로, 호스트의 모든 폴더가 보인다고 생각하면 안 됩니다.

| 작업 | Docker | Apptainer |
|---|---|---|
| 홈 폴더 사용 | 명시적으로 연결 | 기본 설정에서 연결 |
| 현재 작업 폴더 사용 | 명시적으로 연결 | 기본 설정에서 연결 |
| /project 같은 추가 폴더 | --mount 또는 -v | --bind 또는 --mount, 관리자 설정 |
| 입력을 읽기 전용으로 연결 | ro 또는 readonly | ro |

예를 들어 `/project/seon`의 소유자 UID가 1000이고 권한이 700이라면 소유자만 접근할 수 있습니다.

| 실행 조건 | 일반적인 결과 |
|---|---|
| Docker에 폴더를 연결하지 않음 | 해당 호스트 폴더가 보이지 않음 |
| Docker에 연결하고 UID 2000으로 실행 | 접근 거부 |
| Docker에 연결하고 UID 1000으로 실행 | 접근 가능 |
| Apptainer에 연결하고 호스트 UID 1000으로 실행 | 접근 가능 |
| 다른 연구자가 Apptainer에 연결해 실행 | 그 계정이 원래 접근할 수 없다면 접근 거부 |

### 같은 파일 처리 작업을 나란히 읽어 보세요
입력·출력 폴더와 이미지가 준비되어 있다고 가정합니다. 두 예시 모두 입력을 읽기 전용으로 연결하고 결과를 호스트 출력 폴더에 저장합니다.

```bash
# Docker: 사용자와 폴더 연결을 지정
docker run --rm \
  --user "$(id -u):$(id -g)" \
  --mount "type=bind,src=$PWD/input,dst=/input,readonly" \
  --mount "type=bind,src=$PWD/output,dst=/output" \
  alpine:3.21 sh -c 'wc -l /input/samples.tsv > /output/line-count.txt'

# Apptainer: 실행 사용자 권한은 기본적으로 유지
apptainer exec \
  --bind "$PWD/input:/input:ro" \
  --bind "$PWD/output:/output" \
  alpine.sif sh -c 'wc -l /input/samples.tsv > /output/line-count.txt'
```

두 예시에서 연결한 출력 폴더에 쓰면 **실제 호스트 파일이 생성되거나 변경**됩니다. SIF 내부가 읽기 전용이어도 연결된 출력 폴더에는 쓸 수 있습니다. 반대로 입력 연결의 `ro`를 생략하면 프로그램이 실제 입력 파일을 바꿀 수도 있습니다.

> **읽기 전용 연결의 범위:** `:ro`는 그 연결 경로만 보호합니다. Apptainer가 같은 데이터를 홈이나 현재 폴더의 다른 쓰기 가능한 경로로도 보여준다면, 그 경로를 통한 수정까지 막아주지는 않습니다. 필요한 경우 `--contain`과 `--no-mount cwd` 등으로 기본 연결을 줄이고 입력·출력을 명시적으로 연결합니다. 실제 적용 범위는 서버 설정을 확인합니다.

### Docker 이미지를 가져와도 이미지 내부 권한은 남아요
이미지의 `/opt/analyze.py`가 UID 2000 소유이고 권한이 700이라면, Docker에서 UID 2000으로 실행할 때는 사용할 수 있습니다. Apptainer에서 호스트 UID 1000으로 실행하면 권한 오류가 날 수 있습니다.

공유 분석 이미지를 만들 때는 실행 파일과 라이브러리를 일반 사용자가 읽고 실행할 수 있게 준비하고, 결과는 호스트의 연결된 작업 폴더에 저장합니다. 이미지 내부 계정 전용 경로인 `/root` 등에 분석 도구를 두면 일반 사용자 실행에서 문제가 생길 수 있습니다.

## 10. 대규모 연구 환경에서 유용한 이유와 한계
**Apptainer가 특히 잘 맞는 환경은 여러 연구자가 공유하는 HPC·Slurm 클러스터입니다.** 서버 수가 많다는 이유만으로 모든 환경에서 Docker보다 유리한 것은 아닙니다.

| 연구 클러스터의 요구 | Apptainer가 맞는 이유 | 남는 관리 작업 |
|---|---|---|
| 연구자마다 다른 도구 버전 | 각 이미지에 프로그램 환경 준비 | 이미지 버전과 사용 기록 관리 |
| 공용 서버의 사용자 권한 유지 | 기본적으로 각자의 UID·GID 사용 | 데이터 권한과 폴더 연결 확인 |
| 여러 노드에 환경 배포 | SIF 파일을 공유하거나 복사 | 공유 저장소 부하와 로컬 배치 관리 |
| Slurm으로 CPU·메모리 할당 | 배치 스크립트에서 일반 명령처럼 실행 | 자원 신청과 사이트 규칙 준수 |
| GPU·MPI 자원 사용 | 호스트 자원과 연동 가능 | 드라이버·MPI·Slurm 호환성 확인 |

### Slurm과 Apptainer는 서로 다른 일을 합니다
다음은 Slurm이 설치된 서버의 **읽기용 배치 스크립트 예시**입니다. 파일을 작성하는 것만으로 작업이 제출되지는 않습니다. `/project`의 이미지·스크립트·데이터가 준비되어 있다고 가정합니다.

```bash
#!/bin/bash
#SBATCH --array=1-100
#SBATCH --cpus-per-task=4
#SBATCH --mem=8G

apptainer exec --bind /project:/project \
  /project/images/analysis.sif \
  python /project/scripts/analyze.py \
  --sample "$SLURM_ARRAY_TASK_ID"
```

| 부분 | 맡는 일 |
|---|---|
| --array=1-100 | Slurm에 100개 작업으로 구성된 배열 작업 요청 |
| --cpus-per-task=4 | 각 작업의 태스크에 CPU 4개 요청 |
| --mem=8G | 작업에 노드당 메모리 8G 요청 |
| SLURM_ARRAY_TASK_ID | 각 작업의 번호. 여기서는 샘플 번호로 전달 |
| apptainer exec | 준비된 이미지 환경에서 분석 프로그램 실행 |

100개 작업이 모두 동시에 실행되는 것은 아닙니다. 사용 가능한 자원과 클러스터 정책에 따라 대기합니다. CPU 4개를 신청했다고 Python 코드가 자동으로 4개를 사용하는 것도 아닙니다. 프로그램의 병렬 실행 설정이 별도로 필요합니다.

**Slurm은 작업 배치와 자원 할당, Apptainer는 프로그램 실행 환경을 담당합니다.** Apptainer 자체가 분석을 여러 노드로 자동 분산하지 않습니다. MPI 계산은 호스트와 이미지의 MPI 및 PMI/PMIx 연동 구성을 맞춰야 합니다.

### 단점도 함께 기억하세요
- **기본 연결이 편한 만큼 파일 노출도 늘어납니다.** 컨테이너 프로그램도 내 권한으로 내 파일을 바꿀 수 있습니다. 필요한 폴더만 연결하고 입력은 읽기 전용으로 관리합니다.
- **같은 이미지가 모든 실행 조건을 고정하지는 않습니다.** 호스트 커널·CPU 구조·환경변수·GPU 드라이버·외부 데이터의 영향을 받습니다. `--cleanenv`로 호스트 환경변수 유입을 줄일 수 있지만 모든 조건을 고정하는 것은 아닙니다.
- **SIF 내부를 즉석에서 수정하기 불편합니다.** 패키지 변경은 보통 이미지 재빌드로 관리합니다. sandbox나 overlay도 있지만 이번 입문 범위에서는 다루지 않습니다.
- **배포가 간편해도 저장소 병목은 남습니다.** 많은 작업이 동시에 공유 저장소의 이미지를 읽으면 부하가 생길 수 있어 로컬 디스크 복사 같은 운영 방식을 검토합니다.
- **웹·DB 서비스 운영에서는 다른 요구가 생깁니다.** 네트워크·재시작·상태 저장을 관리할 때 Docker 중심의 도구가 더 편한 경우가 있습니다.

**선택 기준은 계산 속도 우열보다 운영 환경과 작업 목적입니다.** 연구 분석 배치 작업은 Apptainer, 개발 환경과 서비스 운영은 Docker가 자연스러운 경우가 많으며 실제 선택은 서버 정책에 따릅니다.

## 11. 컨테이너를 사용해도 서버 자원은 함께 씁니다
도구 세트를 가져왔다고 연구실 책상이 새로 생기지는 않습니다. Apptainer도 실제 서버의 CPU·메모리·디스크를 사용합니다.

- 이미지 파일과 다운로드 캐시도 저장공간을 차지합니다.
- 결과와 임시 파일이 어느 디스크에 저장되는지 확인합니다.
- CPU·메모리는 서버에서 허용하거나 할당받은 범위로 사용합니다.
- 작업 제출 시스템이 있는 서버에서는 그 시스템으로 자원을 신청합니다.

**Apptainer가 자동으로 자원을 제한하거나 다른 사용자에게 영향을 전혀 주지 않게 해 주는 것은 아닙니다.** 앞에서 배운 경로·권한·자원 확인은 그대로 필요합니다.

## 12. 이번에는 왜 설치 실습을 하지 않나요?
Apptainer와 SingularityCE를 실행하려면 Linux 환경과 해당 도구 설치가 필요합니다. Windows는 WSL2, macOS는 Linux 가상 머신 등의 추가 준비가 필요합니다. **Docker Desktop을 설치한 것과 Apptainer를 설치한 것은 별개입니다.**

이번에는 환경을 더 설치하기보다, 연구 서버에서 안내를 받았을 때 이해할 수 있도록 개념과 명령의 흐름만 확인합니다.

## [확인 활동] 파일이 보이는데 왜 쓸 수 없나요?
호스트 사용자 UID는 1000이고 출력 폴더 소유자도 UID 1000, 권한은 700입니다. Docker 이미지는 `USER 2000:2000`으로 설정되어 있습니다.

1. Docker에서 출력 폴더를 연결만 하면 결과를 쓸 수 있나요?
2. Docker 실행 시 무엇을 추가하면 소유자 UID·GID로 실행할 수 있나요?
3. Apptainer 기본 실행에서는 어떤 UID로 실행하나요?
4. 출력 폴더를 읽기 전용으로 연결하면 UID가 같아도 쓸 수 있나요?

<details markdown="1"><summary>[답지] 해설 보기</summary>

1. 일반적인 Linux Docker 구성에서는 쓸 수 없습니다. 연결은 되었지만 실행 UID 2000에 권한이 없습니다.
2. `--user "$(id -u):$(id -g)"`로 호스트 UID·기본 GID를 지정합니다. 보조 그룹이나 프로그램의 계정 요구는 별도 확인합니다.
3. 실행한 호스트 사용자의 UID 1000입니다. 이미지의 USER 설정은 기본 실행에서 무시됩니다.
4. 쓸 수 없습니다. 읽기 전용 연결은 그 경로를 통한 쓰기를 막습니다.

</details>

## 자주 헷갈리는 질문

**Apptainer가 Docker보다 무조건 더 좋은가요?**
사용 목적과 서버 환경에 맞춰 선택합니다. 이번 개인 PC 실습은 Docker Desktop을 사용하고, 연구 서버에서는 제공되는 도구를 사용합니다.

**SIF 파일을 받으면 분석도 끝난 건가요?**
도구만 준비된 상태입니다. 입력 파일과 실행할 명령을 지정해야 실제 작업이 시작됩니다.

**컨테이너니까 남의 파일도 열 수 있나요?**
내 사용자에게 허용된 파일만 사용할 수 있습니다. 컨테이너는 서버의 접근 권한을 없애 주지 않습니다.

## 이 장의 정리

- Docker와 Apptainer는 모두 준비된 도구와 실행 환경으로 작업하도록 돕는다.
- SIF는 이미지 파일이고, `exec`는 그 환경에서 명령을 실행하는 것이다.
- 결과를 저장할 폴더를 연결하고, 그 경로에 결과를 쓴다.
- 실행 사용자의 UID·GID와 폴더 연결을 구분한다. 파일이 보여도 권한이 없으면 사용할 수 없다.
- Slurm은 작업과 자원을 관리하고, Apptainer는 프로그램 환경을 제공한다.
- 연구 서버의 권한과 자원 사용 규칙을 지킨다.
